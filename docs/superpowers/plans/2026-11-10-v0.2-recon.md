### 2. Grow up (current) or grow down (new default) in auto-grow mode

**Combat Trail.** modules/Hud.lua render() (line ~586, the Hud.lua:470+ block offset 117) calls `ui.frame:SetSize(width(), contentTop() + body.height + contentBottom())` on every redraw, and the height follows the body's stack. **DPS Race.** DR has no auto-grow. Its window is a fixed size from windows.hud plus a grip, so nothing comparable exists. DR savePosition is the same pattern (modules/Hud.lua ~368-376).

Add a Layout > Size dropdown row: "Grow" with "Down (the top stays put)" / "Up (the bottom stays put)". ### 4. Bug: the live DPS tile shows a long raw decimal ('77.142857...', '30.1904761...') in CT while DR shows '31.7' in the same Retail session

**Combat Trail.** The formatter is identical. `diff` of CT and DR modules/Format.lua differs only in comments and DR's race helpers. LADDER, CHECK_VALUE 2763000 -> "2.76M", build(), instance() and Number() are byte-identical (CT Format.lua:29-109). Compat.NewNumberFormatter is identical (CT core/Compat.lua:419-427, DR core/Compat.lua:132-139; it prefers C_StringUtil.CreateAbbreviatedNumberFormatter, then CreateNumericRuleFormatter). Format.Reset has no caller in CT outside its definition (Format.lua:77), so it is not the cause. The TOC order is fine (Format at modules\Format.lua, after core and Meter, and it is built lazily on first Number call). The display path is identical in shape: CT Hud_States.lua:306-308 setValue -> `fs:SetText(NS.Format.Number(value))` and SetLive :445-451 `setValue(self.w.dps.value, player and player.dps)`. DR Hud_States.lua:983 `setKpi(self.w.dps, NS.Format.Number(live.dps))`. THE REAL DIFFERENCE is the value fed in. CT reads the live figures BY SESSION ID: Hud.lua readLive (~:742-751) `id = sessions[#sessions] or fight.sessionID`, then Meter.ReadLive(id). That goes through liveSource -> `GetCombatSessionSourceFromID(liveID, ...)` and liveSession -> `GetCombatSessionFromID` (CT Meter.lua:486-494) for all three DPS rungs (source, localRow, dpsType at Meter.lua:496-546). DR always reads `GetCombatSessionSourceFromType(SESSION_CURRENT, ...)` (DR Meter.lua:200-215, 254-269). DR's own note at Meter.lua:176-177 says the Current-type source carries NO amountPerSecond on the live client, so DR is served by a lower rung (localRow / dpsType). CT's ID-scoped source evidently does carry it, so CT's 'source' rung serves a raw rate. The digits confirm a raw quotient total/whole-seconds: 77.142857 = 540/7 and 30.190476 = 634/21, i.e. 77.1K and 30.19K with the 'K' lost to the tile's ellipsis. The magnitude matches DR's 31.7(K) in the same session. Why it is not truncated: the client formatter's breakpoint math truncates only via the integer significand, (n / significandDivisor) floored, then / fractionDivisor. build() checks only an INTEGER (2763000), so a formatter that passes a fractional n through unfloored ('30.1904761904K') is trusted. 'Sometimes' fits: the served rung changes (servedRung, Meter.lua:526-543) and some rates are integer-valued. The same latent defect exists in DR for any fractional input. CT also has no tests/test_format.lua (DR has one), and CT's harness installs no formatter mock (`grep CreateAbbreviated tests/*.lua` finds nothing), so Format.Number in CT tests always takes the Lua abbreviate() fallback and this path is untested. Secondary instance of the same defect: the over card's merged.dps is a PLAIN Lua float (Meter.lua:299-303 rateOf total/duration, Fight.lua:162-165 rate). It also goes to the client formatter first (Format.lua:96-99) and would render raw too. Recorder rounds to one decimal (round1, Recorder.lua:191-195), but 77.1 is still fractional.

**DPS Race.** DR modules/Format.lua is the same code with the same latent defect. DR's live DPS comes from GetCombatSessionSourceFromType(SESSION_CURRENT) (DR Meter.lua:254-269), whose source lacks amountPerSecond per DR Meter.lua:176-177, so a different rung serves a value the formatter renders cleanly. DR's test mock formatter (DR tests/mock_widgets.lua:63-84) floors `scaled*factor`, so it models the truncation the real client does not do for fractions. That is why the defect is invisible in both suites.

A constructor that fails it is not trusted. Try the second constructor too: make Compat.NewNumberFormatter return the candidates in order, or add Compat.NumberFormatterCandidates(), so build() can fall through from CreateAbbreviatedNumberFormatter to CreateNumericRuleFormatter. (b) For PLAIN numbers, never use the client formatter: move `local plain = Secrets.PlainNumber(v); if plain then return abbreviate(plain) end` ABOVE the formatter call. abbreviate() floors in Lua, which is legal on a plain value.
